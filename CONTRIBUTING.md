# Contributing to GoQulient

Thanks for helping. Bug reports, fixes and features are all welcome; for anything large, open an issue first so we
can agree on the approach.

## Setup: Docker only
You need **Docker** with Compose v2, and nothing else: Rust, Node and the test databases all run in containers of the
compose project `goqulient` (`docker-compose.yml`). It publishes the databases on `127.0.0.1` ports 25432, 23306 and
27217 only, so it doesn't collide with databases you already run. A linked git worktree gets its own project and ports
([Parallel worktrees](docs/TESTING.md#parallel-worktrees)).

```bash
scripts/dev.sh up                     # test databases (PostgreSQL 17, MySQL 8.4, MongoDB 7) + engine/vscode containers
scripts/dev.sh engine test [filter]   # Rust: unit, protocol, database integration and parity tests
scripts/dev.sh engine check           # rustfmt --check + clippy -D warnings
scripts/dev.sh engine build           # release build (Linux)
scripts/dev.sh vscode test            # extension: typecheck + Node tests against the engine's debug build
scripts/dev.sh vscode build           # bundle the extension and webviews into vscode/dist
scripts/dev.sh vscode e2e             # the extension in a real VS Code (xvfb) against the test databases
scripts/dev.sh vscode run [folder]    # try it in your own VS Code (needs a native cargo for the engine)
scripts/dev.sh vscode package <dir>   # VSIXs from engines downloaded from a release run (docs/PUBLISHING.md)
scripts/dev.sh engine shell | vscode shell
scripts/dev.sh down                   # remove containers and volumes
```
Test suites, the e2e test, the webview harness and the optional Atlas test: [docs/TESTING.md](docs/TESTING.md). How
the code is organised: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Pull requests
- **Tests are required.** Every behaviour change or bug fix comes with a test that fails without it: Rust unit or
  integration tests in `engine/`, Node tests in `vscode/test/`, and the e2e suite when it needs a real VS Code. Before
  you push, run `engine check`, `engine test` and `vscode test` (and `vscode e2e` for tree, view or connection
  changes). CI runs the same on Linux, macOS and Windows.
- **Safety rules are not negotiable**: deadlines on every network wait, row and cell caps, read-only enforced by both
  the client and the database session, confirmation for destructive statements, single-row edits, one runtime, secrets
  only in secure storage. See [AGENTS.md](AGENTS.md#safety).
- **Don't edit `parity/`.** The fixtures are generated by the Goku app's test suite and change through a sync pull
  request from the app's repository. If your change breaks a parity test, the change needs another look (or an issue).
- Keep the style of the surrounding code (`cargo fmt`, max width 120; TypeScript as in `vscode/src`). Update the docs
  in the same pull request when behaviour changes.
- Don't commit secrets, real connection strings or `.env` files (only `.env.example` is tracked).

## Commit messages
[Conventional Commits](https://www.conventionalcommits.org/): `feat: …`, `fix: …`, `docs: …`, `test: …`, `refactor: …`,
`ci: …`, `chore: …`, with an optional scope (`feat(vscode): …`, `fix(engine): …`) and `!` for breaking changes. The
changelog and the version are built from them by release-please ([docs/RELEASING.md](docs/RELEASING.md)), so the
subject should say what changed for a user.

## Coding agents
Agents (Claude Code, Codex, …) start at [AGENTS.md](AGENTS.md); `CLAUDE.md` includes it. How we write Rust in the
engine (invariants, errors, async, API shape, tests, review checklist) is the project skill
[`.claude/skills/rust-engine/SKILL.md`](.claude/skills/rust-engine/SKILL.md); it's worth a read for human contributors
too.
